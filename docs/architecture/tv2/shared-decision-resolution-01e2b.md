## 6. Message Requests policy and alternatives

### 6.1 Separate concepts

Friend Request asks for a social relationship. Accepted friendship is a persisted relationship fact. Message Request asks for contact/chat consent; its acceptance may grant chat permission without friendship, or may require an explicit friendship transition. **That choice remains unresolved.** DIRECT authorization is a current server decision using selected consent/relationship facts, both-direction block and account eligibility. Conversation existence and canonical UUID do not authorize access.

Block/unfriend are authority transitions, not automatic history deletion or period recreation. Existing legitimately authorized history can remain readable under TV1 HC06, subject to current disclosure policy for history/replay/media. A stranger's intro/request has never acquired ordinary authorized Message history and cannot inherit that retention rule. GROUP membership and GroupInvitation remain separate resources/policies.

### 6.3 Proposed behavioral state machine and authority

Use descriptive states only: awaiting recipient decision; accepted; declined; cancelled; invalidated by block; optionally expired under selected time policy. These are not approved enum values. Sender can submit a permitted bounded request, inspect own authorized projection and cancel while pending. Only the intended recipient accepts/declines; either party can block within TV1 policy; report authority and moderation routing need owner selection. Never trust client actor/status/relationship/role. Accepted cannot be reverted by a stale cancel; terminal requests cannot reactivate by replay. Reissue needs a fresh identity and policy-approved cooldown rather than rewriting history.

Crossed Message Requests must not auto-grant authorization; either deduplicate a canonical pair with directional intents or retain two directional requests and serialize acceptance. Select one semantics, including what happens to the other pending request. Crossed Friend Requests expressly require acceptance. Do not equate the two resource keys. Define duplicate same-payload replay versus conflict only after disclosure; hide inaccessible request existence.

Spam/abuse design must specify bounded pending counts per sender/recipient/pair, per-account/IP/device budgets as appropriate, cooldown/reissue, recipient suppression, report escalation, safe preview and notification redaction. Values/provider/moderation workflow are unselected. Intro text needs its own validation and retention; no attachments or READ/TYPING before Accept. Hidden/opt-in E.164 lookup is independent of request eligibility; no phone enumeration via create errors, quotas or notifications.

### 6.4 Transaction, race, idempotency and unknown commit

Acceptance must serialize request state, authoritative consent/friend/block/account facts and canonical pair creation under one selected global order. Validate participant, request generation/version, current recipient decision authority, current block/eligibility and required friendship transition. Persist acceptance and any chat grant plus canonical conversation/member/period facts and commit-coupled event intent atomically; publish no full access before commit. Domain owners must decide whether this is one physical transaction and how repositories join it. No separate asynchronous membership creation that temporarily grants partial access.

Block wins first: request/accept/create/send is denied under current policy, with no new access/message. Accept wins first: committed creation may exist, then block fences new interaction, pending fanout and requests. Final response/list/replay/media admission still checks current disclosure; existence does not entitle delivery. Cancel/decline/expiry and acceptance must have a single serial terminal outcome. Both-order deterministic future tests must inspect committed rows, grants and events; lock strategy is not selected by this prose.

Canonical pair uniqueness is about the stable two server UUIDs with a reviewed deterministic comparator, never phone or array order. Concurrent A→B/B→A acceptance/create must yield one conversation and no half-membership. Uniqueness-conflict reread must use a usable transaction and recheck current ACL; do not query inside an aborted transaction or return a blocked winner. Existing canonical conversation may be reopened only under current authorization, not duplicated. Unfriend/block must not automatically generate new periods or new pair identities.

Request-create and accept need selected idempotency semantics and keys distinct from clientMessageId unless a reviewed contract explicitly maps them. Timeout after dispatch means unknown commit. Reconcile an entitled request/grant/conversation under original operation identity; never create a new request/message blindly. Hidden/blocked reconciliation must preserve concealed error parity, with no hidden commitment oracle. A lost response never proves acceptance failed or permits silent resend as ordinary Message.

### 6.5 Discovery, history, events and ownership

Pending requests belong to a separate authorized inbox/outbox projection. They must not leak into ordinary conversation discovery, history pages, replay watermarks, receipt roster, unread/read aggregation, attachment grants, translation cache or global participant lists. If B is ever selected, every one of these branches requires an explicit restricted capability and compatible clients; no enum-only admission shortcut.

Do not retroactively convert intro into immutable send/ACK history or grant access to an existing conversation's unrelated hidden content. Existing authorized conversations after unfriend/block follow D06's retained-history proposal plus current ACL, while new interactions, typing and receipt writes stop as selected. Unblock does not itself recreate friendship or accepted consent. Historical receipt visibility and old signed URLs need independent policy; block cannot recall downloaded bytes.

Acceptance/decline/cancel/block and canonical creation need durable participant-scoped account discovery or an equivalently complete polling strategy, recipient projection and notification suppression after authority changes. Only entitled identities/content appear; no public membership event is invented. Do not add an eleventh FIX3 event silently.
